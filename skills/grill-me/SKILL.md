# Grill Me

## 개요

AI 개발 실패의 대부분은 모델이 코드를 못 짜서가 아니라 **요구사항이 끝까지 명세되지 않았기 때문**에 발생한다. 이 스킬은 코드를 한 줄 쓰기 **전에** 아이디어를 심문해서 그 문제를 막는다.

핵심 원칙: **한 번에 하나의 질문만 하고, 내 추천 답을 함께 제시하며, 코드베이스에서 스스로 답할 수 있는 질문은 직접 탐색해 해결한다.**

## 프로세스

### 1. 출발점 파악

사용자가 준 컨텍스트를 먼저 읽는다. 코드베이스·기존 스펙·러프한 메모를 가리켰다면 **반드시 먼저 읽는다.** 이 단계를 건너뛰지 않는다.

### 2. 한 번에 하나의 질문만

**가장 중요한 규칙. 한 메시지에 질문 두 개 이상 금지.**

각 질문은:

- **하나의 구체적 결정/모호함**에만 집중
- **내 추천 답**과 근거 포함
- **왜 중요한지**(무엇이 이 결정에 달려 있는지) 설명

질문 형식:

```
**질문 N: [주제]**

[실제 질문.]

추천: [내 제안 답과 근거.]

[이게 왜 중요한가 / 무엇이 이 결정에 달려 있는가.]
```

### 3. 코드베이스를 탐색해 스스로 답하기

사용자에게 묻기 전에, 코드를 읽어 직접 답할 수 있는지 먼저 확인한다. 가능하면 묻지 말고 직접 확인한다. 사용자에게는 **그들만 결정할 수 있는 것**(제품 결정, 우선순위, 트레이드오프, 선호)만 묻는다.

> 이 저장소 환경 참고: 코드 작업 대상이 Kotlin/Spring(Hexagonal), TypeScript/React라면 `~/.claude/architecture-guides/`의 해당 가이드를 먼저 읽고, 아키텍처 경계·레이어 관련 질문은 가이드 기준으로 추천 답을 잡는다.

### 4. 점진적으로 스펙 쌓기

진행하면서 결정된 것을 추적한다. 몇 개 질문마다 현재 스펙 상태를 요약해 사용자가 형태를 볼 수 있게 한다.

### 5. 멈출 때를 알기

다음이면 심문을 멈춘다:

- 주요 결정이 모두 내려짐
- 남은 질문이 내가 스스로 정할 수 있는 구현 디테일뿐
- 사용자가 준비됐다고 말함

그다음 최종 명세를 작성한다.

## 최종 명세

심문이 끝나면 다음을 포함한 구조화된 스펙을 작성한다:

- **목표(Goal)**: 무엇을 왜 만드는지 한 문장
- **요구사항(Requirements)**: 합의된 구체적 동작
- **비목표(Non-goals)**: 명시적으로 하지 않기로 한 것
- **미해결 질문(Open questions)**: 아직 안 풀린 것
- **구현 노트(Implementation notes)**: 인터뷰 중 내려진 기술 결정

사용자가 원하면 파일로 저장하거나, 다음 단계로 넘긴다.

## 다음 단계 연계

명세를 완료하면 아래를 **안내만 한다.** 직접 실행하지 않는다 — 전부 오케스트레이터이고,
user-invoked 끼리는 서로 호출할 수 없다. 무엇을 실행할지는 사용자가 정한다.

- `superpowers:writing-plans` — 스펙을 bite-sized 작업 계획으로 분해
- `superpowers:brainstorming` — 더 발산적 탐색이 필요할 때
- `/dev-cycle`, `/mvp` — 이 저장소의 기존 개발/기획 워크플로우

## 핵심 규칙

- **한 번에 하나의 질문.** 절대 묶어 묻지 않는다.
- **항상 추천 답을 제시.** 열린 질문만 던지지 말고 최선의 추측과 근거를 준다.
- **묻기 전에 탐색.** 코드베이스에서 답할 수 있으면 직접 답한다.
- **코드를 쓰지 않는다.** 이 스킬은 구현이 아니라 명세 단계다.
- **주기적으로 요약.** 진화하는 스펙을 계속 보이게 한다.
